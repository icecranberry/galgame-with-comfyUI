# 神说全量测试与工具覆盖验收

日期：2026-11-05（Asia/Shanghai）。环境：Windows / Node.js v22.16.0。测试对象：当前工作区的神说后端、工具注册表、业务接口桥接、相关前端逻辑，以及配置模型 `deepseek-v4.1-flash-1017` 的工具选择。

本文保留修复前的基线和事故记录，不代表修复后的当前结论。后续实现与验证见 [修复验收记录](./修复验收记录.md)。

## 直接执行

**验收结论：暂不通过。** 改名、基础外观的确认机制能够工作，但确认范围不符合本次要求，存在不必要的确认、绕过确认的写操作、表情包功能断链，以及缺失能力被世界事件替代的实际模型调用偏移。

本次交付为测试、可重跑用例和证据文档，未修复产品逻辑。没有提交 commit，没有修改原有暂存的 `web-ui/src/views/TavernView.vue`。

### 2. 数据隔离与限制

- 测试业务数据来自合成角色和独立 SQLite `:memory:` 库；文件型测试库限定系统临时目录。没有复制真实角色、聊天、世界观或日程用于测试，也没有向真实库执行业务 SQL。
- 真实模型调用使用现有环境连接配置，只发送合成资料。读取工具使用合成 fixture，模型提出的写工具在执行前截停；没有让模型操作真实系统。
- 新增可复用隔离入口 `agent-core/test/helpers/godAuditIsolation.mjs`，在 SQLite native binding 上禁止打开临时目录外的库，并限制外部 HTTP/fetch。真实模型测试须显式开启，仅放行配置的模型服务。
- **隔离验证事故记录：** 初版仅替换 CommonJS `require.cache`，不能可靠拦截 ESM 导入。一次负向验证因此打开了真实库连接，随后断言失败退出，未执行查询或业务写入。不能声称本次“从未打开过真实库”。已改为 native binding 拦截，并用工作区内的虚拟数据库路径重新验证拒绝打开，同时验证内存库可正常使用。抱歉这次隔离保护没有在首次验证时生效。
- 普通自动化中的异步人设浓缩已固定到本地模型 fixture，避免测试后台任务使用环境中的真实模型或在数据库关闭后继续写入。
- 临时原始日志和辅助脚本位于系统临时目录 `linshe-god-acceptance-20261105`，不在仓库中。结束时自动审批策略拒绝了递归及非递归清理，仅返回“blocked by policy”，未提供更具体原因；因此保留该目录，没有绕过策略删除。

### 4. 缺陷清单

#### BUG-01 / P1：修改已有数据的工具能够绕过确认

当前 `changePolicy.js` 仅用固定 `CONFIRMED_TOOLS` 名单决定是否确认，把大量日常玩法作为例外。这与“已有数据修改需要确认”的要求不一致。

| 用户需求示例 | 当前工具 | 当前实际路径/效果 | 验收 |
| --- | --- | --- | --- |
| 重排她今天的日程 | `regenerate_schedule` | 直接请求生成并覆盖模板、快照及睡眠同步 | 确认前已派发 |
| 下午两点改去图书馆 | `set_schedule` | 今日直接调用日程修改服务 | 确认前已执行服务 |
| 收下这个道具 | `collect_item` | 修改已有道具领取状态 | 确认前已派发 |
| 把这个道具给她用 | `use_item` | 消耗库存并产生效果 | 确认前已派发 |
| 打电话叫醒她 | `wake_character` | 增加叫醒次数，可能更改睡眠状态 | 确认前已派发 |
| 取消这条媒体收藏 | `set_media_favorite` | 更新已有帖子的收藏状态 | 确认前已派发 |
| 临时变成红龙两小时 | `inject_character_state` | 新建形态，同时停用已有专属形态 | 真实路由已证实停用旧外观，无确认 |
| 重写已有日记 | `generate_diary` | 同角色同日期冲突更新状态，后台重写内容 | 未按目标存在性分流，确认前已派发 |
| 重做已有表情提示词 | `generate_emoji_prompt` | 更新 `character_emojis.prompt/style/status` | 确认前已派发 |
| 重做已有表情图片 | `generate_emoji_image` | 更新已有表情状态与图片记录 | 确认前已派发 |

证据：`godSaysAcceptance.test.js` AC-05、AC-06；真实变身写入见 `godSaysAcceptanceHttp.test.js` AC-H03。日记和表情覆盖语义另核对了原业务源码；并非每一行都完成了真实生成落库。

建议：由后端按业务目标判断“新增/修改/删除”，生成日记、表情等还要看目标是否已经存在。不要让模型通过“临时变身”绕过本应保护的既有外观切换。

#### BUG-02 / P2：纯新增内容被要求确认

固定名单包含创建群聊、专属外观、关系、世界观、朋友圈话题、奇遇类型、媒体等纯新增操作。新增合同用例对其中 7 个工具逐项复现了 `awaiting_confirmation`；新角色、媒体板块、表情包组也在名单中，已有集成/源码可追溯。

例如“新增一套蓝斗篷，先别启用”，只是插入一条禁用外观，仍需点击确认。用户要求新增不确认，启用已有外观则应该确认，两者应区分。

证据：AC-07；AC-H02 验证其确认后确实仅新增禁用外观。已有 `godSaysHttp.test.js` 甚至断言“建群前必须等待确认”，说明旧测试合同和本次新需求相反。

#### BUG-03 / P2：改名的确认卡不显示新旧名字

复现：“把验收角色甲改名为晚晴，其他都不改。”提交 `update_character`，草稿 `args.display_name` 有新名字，但后端 `prepare()` 只生成完整人设 `preview`。前端 `godChangeFields()` 遇到 `preview` 直接返回，丢掉名称字段。

结果：用户看到人设正文没有变化，确认后却真的改名。机制有确认，但确认内容不完整。

证据：AC-02 直接走前端实际字段转换函数；AC-03、AC-H01 证实确认后名称真实改变。

#### BUG-04 / P2：只改名字也必须让模型重传整个人设

`update_character` schema 强制要求 `base_prompt`。仅提交 `character_id + display_name` 会被拒绝。为了改几个字，模型必须读取、复制完整人物卡，扩大 token 成本与无关内容误改的可能。

证据：AC-11。建议独立 `rename_character` 或允许字段级 `update_character`，只对实际修改字段做预览、快照与写入。

#### BUG-05 / P2：外观草稿的输出约束只写在提示词里，校验不完整

`validateReplacement()` 会拒绝空内容、代码围栏、一/二级标题，但接受 `{"appearance":"红发蓝眼白裙"}`，也接受 `### 其他人格`。这些结果与“只返回完整外观正文，不带章节或 JSON”的工具合同冲突，仍可成为待确认草稿。

证据：AC-12 两条失败断言。建议校验所有 Markdown 标题级别、JSON/包装格式，并保留全文差异审核。格式校验无法自动证明“蓝眼、白裙等未要求改动的语义一定保留”，不能只依赖一条提示词承诺。

#### BUG-06 / P1：新表情包无法从空白套装生成第一条表情

真实复现链路：

1. 调用 `create_emoji_set`，确认后成功创建新套装。
2. 查询 `character_emojis`：该套装为 0 条。
3. 调用已注册的 `generate_emoji_prompt`。
4. 原单表情接口先查表情行，未找到直接返回 404“表情包不存在”，尚未调用生成模型。

系统有 `POST /api/characters/emoji/prompts` 批量生成/初始化接口，但神说没有对应工具。`generate_emoji_image` 又依赖提示词。因此“给她做一套表情包”不是简单工具选择问题，当前工具集合无法闭环。

证据：AC-H04。建议接入原初始化服务，区分“新增首批提示词”与“覆盖已有提示词”；不要在单条重生成工具里伪造完成。

#### BUG-07 / P1：同一个“新增事件”工具能携带参数修改旧事件

`create_world_event` 普通新增不确认，符合要求；但带 `supersedes_id` 时，会直接 `UPDATE` 旧事件为 ended 并修改过期时间，也没有确认。

证据：AC-14 验证独立新增正常；AC-15 使用真实内存事件服务，证实旧事件在确认前已结束。

建议：确认策略必须检查参数和当前目标状态。单看工具名、POST 方法或“新增”标签无法判断副作用。

#### BUG-08 / P1：能力缺失时，用叙事事实代替实际接口操作

真实模型需求：“把小镇的咖啡店改名为星光咖啡。”

第一次边界测试中，模型查询能力后，选择了：

```json
{
  "name": "create_world_event",
  "arguments": {
    "title": "咖啡店改名星光咖啡",
    "fact": "小镇上唯一那家咖啡店已正式改名为「星光咖啡」，招牌、菜单与杯套上的名字都换成了新的；镇上的人从此都以「星光咖啡」称呼它。",
    "duration_minutes": 10080,
    "moment_count": 2,
    "group_count": 1
  }
}
```

小镇实际记录不会改名，反而准备新增世界事实并触发额外社交回应，还臆造“唯一那家”与招牌等事实。写操作在验收中截停，没有落到真实环境。

独立复跑时模型能够正确说明没有小镇能力，并不调用写工具。因此结论是**行为不稳定**，不能用后来一次通过抹掉前一次偏移。

证据：[live-intent-results.json](./live-intent-results.json) 中“缺失小镇工具”的两次有效尝试。系统现有规则已写“小镇专属功能未接入”，仅继续追加自然语言警告不足以可靠阻止此类行为。建议在工具行动类别上区分“叙事新增”与“修改已有实体”；缺少目标实体接口时应明确失败或等待补工具，不得自动降级为制造世界事实。

### 5. 生成提示词与原接口复用检查

| 场景 | 当前实现 | 判断 |
| --- | --- | --- |
| 普通生图 | `generate_image → /api/images/test-style`，中文需求进入原生图规则、角色交叉参考与生图服务 | 不是由天使直接自由写最终模型 prompt；链路与尺寸映射有测试 |
| 场景私服/居家/睡衣 | `generate_scene_outfits → /outfits/generate`，`save:false`，解析完整 JSON 草稿，确认后只写指定槽位 | 已复用业务生成器；已有真实路由 fixture 验证未改其他槽位、确认不二次生成 |
| 基础外观修改 | 神说自己的 `replacementPrompt` 编辑器，读取原文并替换外观段 | 有专用提示词和边界，但未统一使用所有原外观设计规则；格式校验见 BUG-05 |
| 新增专属外观 | `create_outfit` 接收天使直接写出的 `description` 并交给 CRUD 接口 | 不等价于复用服装描述生成器，设计规范主要依赖天使自身生成 |
| 改整个人设 | `update_character` 接收天使生成的完整 `base_prompt` | 确认后原样写入；缺少字段级修改约束，见 BUG-04 |
| 世界观重写 | 原文修订生成器生成完整替换稿，确认后提交冻结正文 | 有完整前后文、冲突检测、确认不二次生成回归 |
| 新角色 | 原 `/characters/generate` 先 `save:false`，确认后保存已生成内容 | 复用了原生成器，但“纯新增不确认”的合同尚未对齐 |

原系统另有 `clothing-appearance-draft`、`expand-appearance-draft`、参考图修外观等接口；它们没有全部开放为神说工具。不能据此断言必须照搬某个 HTTP 路由，但应抽出并共享真正负责描述规范的服务，让不同入口得到相同约束，而不是在多处维护相似提示词。

### 6. 已通过的重要行为

- 改名/基础外观：确认前不写业务内容，取消后再点确认无效；确认后精确应用冻结数据，重复确认不重复写。
- 原数据生成期间或确认前改变、目标删除、版本错误：已有回归验证冲突拒绝；不拿过期草稿覆盖新内容。
- 批量外观：已有用例验证 121 角色固定目标集合，新加入的角色不会混入确认草稿；失败/不确定结果不盲目重放。
- 新图片、用户朋友圈、写信和角色朋友圈投递不产生确认草稿；异步受理与真正完成区分。
- 未注册工具、未知参数和模型伪造 `confirmed:true` 不能绕过 schema 或确认接口。
- 全部模块工具的方法/路径存在于真实注册路由；参数映射测试覆盖路径编号、查询参数、私聊幂等键、尺寸覆盖等。
- 真实模型能够选择正确的基础外观、睡衣槽位、临时变身类型/小时数、图片宽高以及角色朋友圈与用户朋友圈工具。

| 角色同居安排、小镇店铺/居民/建筑操作 | cohabitation、town | 小镇明确未接入，同居没有工具；不得用世界事件伪装实现 |
| 删除/恢复记忆、重新整理记忆、语音绑定、工作流管理 | memory、tts、workflows | 仅查询/部分朗读能力，不是模块全覆盖 |

奇遇选项由玩家推进是仓库既有规则，缺少代选工具属于有意边界。模型凭据、运维与日志等接口也不应为了追求覆盖率全部暴露。

### 9. 后续修复验收门槛

1. 24 条 TODO 应对应修复并移除，不能把断言改回旧行为来“通过”。
2. 改名确认卡必须有新旧名称，改名请求不得要求携带无关人设。
3. 修改已有数据的工具及可覆盖参数必须确认；新增草稿/新内容无额外确认。确认前后都检查目标版本，确认后不再调用生成器改变草稿。
4. 表情包从新建套装到初始化提示词、生成图片、查询结果必须能闭环。
5. 对缺失功能的多次真实模型边界测试，不能再出现用世界事件、改人设等不等价操作替代目标业务操作。
6. 新接入工具同步补齐“读原文/当前状态 → 生成受约束草稿 → 需要时确认 → 原服务执行 → 原数据验收”的合同。

## 深度交互

你的核心目标是“天使真实、准确地替用户完成系统操作”。接口数量多，并不能保证这一点：本次全部模块工具的路由都存在，却仍出现空表情包无法初始化、改名卡不展示名字，以及用世界事件代替店铺改名。

更低成本的路线是先修 **确认分类、精确字段预览、表情包初始化、缺失能力拒绝**，再按真实用户任务补工具闭环。暂时不必把 554 个接口机械注册给模型。

“是否执行 SQL UPDATE”也不是最好的确认边界。发朋友圈会更新任务状态，生图会更新 image_tasks，这些内部写入不应让用户不断确认；反过来，`INSERT` 一个临时变身可能停用旧外观。建议按**用户可见的已有对象是否被替换、删除、切换或消耗**判断，保持你要求的“新增内容直接做、改变已有内容先确认”。

生成规范应属于业务服务，天使负责理解需求和调用服务。名称修改用确定性字段更新；外观和图片等创作需求才交给共享生成器，并由结构/内容边界和最终数据库结果共同验收。这样能减少模型自由发挥造成的偏移，也避免重复维护多套提示词。
