# 项目模块功能与 UI 优化巡查

> 日期：2026-10-24。本文归档本轮桌面实看与代码巡查结论，未实施业务代码修改。

## 1. 巡查结论

现有 Cel Glow / Linshe 设计语言已经比较完整，应继续复用。当前优化收益主要集中在操作可靠性、信息层级与大量内容的查找效率，无需整体更换视觉体系。

建议首先处理以下六项：

| 编号 | 优先级 | 问题 | 用户影响 | 证据类型 |
| --- | --- | --- | --- | --- |
| UI-01 | P1 | 通用弹窗缺少完整焦点管理，嵌套窗口同时响应 Esc | 键盘可能操作到下层窗口；一次退出关闭多层 | 桌面交互复现、代码确认 |
| UI-02 | P1 | 小镇动态播报遮挡顶部标题和状态 | 常规桌面宽度下关键信息互相覆盖 | 桌面截图、代码确认 |
| UI-03 | P1 | 相册初次加载无明显反馈，部分请求失败仅写控制台 | 用户难以区分等待、空内容与失败，也缺少恢复入口 | 加载现象实看、失败分支代码确认 |
| UI-04 | P1 | 设置页“即时生效”文案与手动保存不一致，离页草稿保护不足 | 用户可能误以为修改已保存 | 页面实看、代码确认；未实测草稿丢失 |
| UI-05 | P2 | 日程卡片摘要字号小、颜色过浅 | 正文像禁用信息，阅读费力 | 桌面截图、代码确认；未测量对比度比值 |
| UI-06 | P2 | 普通窗口和控件尚未全部收口，动效时长不统一 | 关闭、反馈、键盘使用及视觉体验不一致 | 代码确认 |

本文 P1 表示建议优先修复、影响核心操作理解或可用性；P2 表示明显体验改进；P3 表示进一步提升效率和视觉细节。此分级不等同于安全漏洞等级。

## 2. 范围、依据与验证方式

### 2.1 设计依据

- [设计系统](design-system.md)与[项目约定](../AGENTS.md)。
- 继续复用 LinsheButton、LinsheInput、LinsheSelect、LinsheSwitch、LinsheTabs、LinsheModal。
- 小镇以 NPC 互动、邀请和奇遇叙事为主链路；人物互动参考 TownDialogueStage，生活面板复用 TownPaperPanel。

## 3. 优先修复项

### UI-01：统一弹窗焦点和最上层退出行为

**现象**：小镇点击 NPC 后打开“状态”，焦点仍停在下层的状态按钮；按 Tab 会进入下层“动态”操作。按一次 Esc 后，状态窗口和 NPC 对话一起关闭，回到地图。

**代码依据**：[LinsheModal.vue](../web-ui/src/components/ui/LinsheModal.vue) 第 5、67 行附近没有完整的对话框语义、打开时焦点迁移、焦点约束及关闭后恢复机制；每个实例单独监听全局 Esc。[TownDialogueStage.vue](../web-ui/src/components/town/TownDialogueStage.vue) 也处理 Esc，下层舞台已有焦点处理，但不能替代上层窗口接管焦点。

**建议**：在 LinsheModal 基座实现统一的焦点生命周期和窗口栈。打开后聚焦标题或合适的首个控件，Tab 留在当前窗口，Esc 仅关闭最上层，关闭后返回触发控件。兼顾 Teleport 下拉框与现有浮动模式，避免各页面重复补丁。

**验收**：NPC → 状态 → Tab/Shift+Tab 不进入下层；第一次 Esc 只关闭状态，第二次才关闭 NPC 对话；关闭后焦点恢复到对应触发入口。暖色与暗夜的焦点提示均可见。

### UI-02：消除小镇顶部信息覆盖

**现象**：在本轮桌面视口且侧栏展开时，动态播报与地图顶部标题、状态条占用同一水平区域，出现遮挡。

**代码依据**：[TownView.vue](../web-ui/src/views/TownView.vue) 中 `.town-activity-ticker`（约第 2528 行）与 `.town-topbar`（约第 2643 行）均绝对定位在顶部；只有较窄容器断点将播报移到下方，中间宽度仍可能发生覆盖。

**建议**：让标题、操作与播报共享可预测的布局区域；按小镇实际容器宽度安排播报换行或移位。长播报应有截断和完整内容入口，不单纯依靠提高 z-index。

**验收**：侧栏展开、收起以及 700～1000px 左右的内容宽度均无互遮；长地点名、长播报、状态数量变化时仍可读、可操作。

### UI-03：区分加载、空内容与失败

**现象**：相册初次进入时内容区短暂空白。代码中首次加载失败和寄信失败主要输出到控制台，用户界面缺少明确结果和恢复入口。

**代码依据**：[Gallery.vue](../web-ui/src/components/Gallery.vue) 第 140、380～399 行附近设置 loading，但模板没有对应的初载骨架或状态；失败只记录日志。[MailboxView.vue](../web-ui/src/views/MailboxView.vue) 第 336～347 行的寄送失败分支只记录日志。相关列表 store 也应按同一口径复查。

**建议**：分别表达初载、成功为空、筛选为空、首次失败、有旧数据的刷新失败、续页失败及提交失败。首次失败提供重试；刷新失败保留旧内容；寄送失败保留收信人与正文，并展示可理解的错误。

**验收**：慢网时可辨识正在加载；断网不展示“没有内容”作为最终结论；重试入口可用；长信寄送失败后内容仍在。不要以持续 Toast 代替页面内可恢复状态。

### UI-04：让保存文案和真实行为一致

**现象**：设置页标题写“修改即时生效，无需重启”，但多个分区需要点击保存。页面存在 dirty 标记，但缺少统一的未保存说明和离页保护。

**代码依据**：[SettingsView.vue](../web-ui/src/views/SettingsView.vue) 顶部说明与多个手动保存按钮、`dirty`、`llmDirty`、`connDirty` 状态并存；本轮搜索未发现对应路由离开或浏览器离开时的统一草稿守卫。未实际编辑配置验证丢失。

**建议**：手动保存区改为“保存后生效，无需重启”，真正立即生效的开关单独说明；在分区标题或紧凑状态行显示未保存、保存中、已保存、失败。切换页面前提供保留草稿或放弃修改的明确路径。

**验收**：用户无需猜测当前修改是否生效；离页后草稿可恢复或已明确确认放弃；保存期间继续编辑不会被旧响应清除未保存标记。

### UI-05：提高日程摘要可读性

**现象**：日程卡片底部摘要很淡、字号偏小，正常内容看起来像禁用说明。独立视觉复核也识别到这一点。

**代码依据**：[CharacterStatusCard.vue](../web-ui/src/components/CharacterStatusCard.vue) 第 446 行附近的 `.card-foot` 使用 `font-size: 0.73rem`、`color: #c5bfb6`。本轮没有测量实际合成背景下的对比度数值。

**建议**：用[主题 token](../web-ui/src/styles/tokens.css)表达次要正文，适当提高字号与颜色对比，保持标题、时间、摘要三级信息层次，不将摘要处理成装饰文字。

**验收**：暖色和暗夜均能轻松阅读摘要；实际测量正文对比度；较长摘要和窄屏换行不压缩时间、状态等关键内容。

### UI-06：收敛普通控件、窗口与动效

**代码依据**：[LinsheModal.vue](../web-ui/src/components/ui/LinsheModal.vue) 默认进入 250ms、退出 180ms、面板动画 340ms；[animations.css](../web-ui/src/styles/animations.css) 也存在不同切换时长。角色详情、背包等仍有自建窗口外壳；MaiBot 有原生 checkbox 开关入口。

**建议**：普通业务窗口逐步使用 LinsheModal；普通表单接入对应 Linshe 控件；统一规定的 300ms 开合和切换。通过基座调整行为与皮肤，避免页面覆盖。保留报刊、日记、信纸和小镇对话的业务内容特色。

**验收**：关闭动作有完整退出动画，结束后才卸载；Esc、遮罩关闭和键盘行为一致；普通控件遵循 token，暖色和暗夜无局部异色。保留减少动态效果偏好的兼容处理。

不将隐藏文件输入、range、聊天主输入、信纸 textarea 和约定允许的独立交互控件一概计为违规。

### 4.1 需要单独记录的实现细节
