## 初始基线时确认的缺口与接入条件（历史记录）

以下描述生产 API 尚未接入时的状态；后续生产实测见下一节，有限基金政策见[实现文档](hd2d-m4-liquidity-policy.md)。

- 当前初始20份原料没有已落盘的生产补货 API，`townBusinessWorkAdapter` 仅提供工作事实和营业状态，不能据此增加库存或结算工资。
- 正常消费的钱累积到工坊，供应商余额没有采购收入变化，基金承担配送支出，没有已实现的业务回流。库存首先枯竭，掩盖基金的长期压力。若将来只补货且不新增业务回流，2000基金、30每单最多承担66单；这是现有单向资金流的算术上界，尚未通过生产场景实测。
- 囤币场景的工坊库存积压20份：当前按供给发布配送，未体现店铺库存上限或真实采购需求。生产 API 需结合库存与在途量限制补货，不能按天无限产出。
- 只消费场景从玩家0元开始，反映无收入入口时无法消费，不是已有财富玩家持续消费压力测试。

已通过 main 向 Archimedes 提交接口协调：生产应有稳定批次/来源、有限投入或资源容量、时间/到达事实、同事务库存与成本分录，以及请求重放和跨epoch约束。API 落盘后新增独立生产场景，保留本基线；不在测试中实现缺失经济政策。采购、公共费用、补助等必须先有实际受限业务 API，再测资金不足与未满足需求。

以上为刻意不启用生产的4场景基线，保留以比较新API效果。

## 已接真实生产API的90天场景

`townProductionService` 落盘后新增第5场景：每日真实配送→30元工坊服务→生产start→供应商/工坊各自真实runner work_shift 5分钟→production.complete。测试不直接写工作证明、节点或库存；移动与时间仍由测试适配器推进。生产批次固定消耗有限节点1、从工坊预留30支付公共费用20、采购6、两工人工资各2，并通过受限 `economy.produceStock` 增加供应商原料1。初始化节点容量200只执行一次。

实测90配送、90服务、90生产全部成功，无缺货/资金不足失败。最终基金1100、玩家0、供应商1140、工坊400、两工人各180；供应商原料20，资源节点剩110。每日账本总量与预留检查继续执行，生产请求重放没有重复工资或入库。

这缓解了正常消费路径断货，但基金每日净支出10，90天减少900，仍非经济平衡。囤币路径没有已付服务来授权生产，因此仍在原料20份后停滞。NPC自主消费、更多需求路径、生产调度/到达真实性和基金长期保障尚需后续实现；不以任意转账补齐差额。

另外2项独立边界测试验证produceStock必须外层同DB事务、缺proof/未扣节点拒绝并回滚、换request/source只返回同一收据、改amount冲突，以及旧epoch或借新epoch重用旧生产拒绝。与Archimedes生产测试中的晚日志故障回滚配合，覆盖节点/输出/工资/证明同事务失败。

## 历史提案：最小有界流动性（提案形成时未实施）

以下保留当时提交 main 决策的原始提案与验收建议，其中“缺少”“未来新增”“未实现”均指提案形成时。后续受限发行、持久政策记录及真实订单证明已实现，当前口径以[有限流动性政策](hd2d-m4-liquidity-policy.md)为准。最终实现要求启用时至少60准备金，不提供低余额救助；正常离线前跳不自动暂停、不累计补发，回拨暂停新发行。回收仍未实现。不要将下列历史建议视为当前已生效规则。

目标仅为保留已有配送入口的短期资金能力，不新增职业、不保证永续经营，不修改当前30报酬或生产分配。先部署指标和拒绝原因，再考虑启用策略。以下数字是供评审的保守测试配置，不是已确定经济参数。

### 已有能力与确实缺少的部分

可复用：显式db/clock/epoch、BEGIN IMMEDIATE、不可变交易/分录、唯一request/source hash、reserve/capture/release、同事务outbox。订单publish先预留资金/库存才产生承诺，取消/到期不支付。普通转账禁止使用issuance账户。

缺少：受策略约束的发行/回收命令、持久化政策总额/时间记录与独立来源凭证。目前seed只表示初始发放；不能每天改seedVersion或sourceKey把它变为补贴。produceStock也只服务有限生产，不能用来补货兜底。

### 建议参数与事务边界

1. 准备金：新普通配送承诺后基金可用余额至少60（2单）；待承诺额仍为30，触发检查线为90。计算必须用balance-reserved，不重复计算已承诺订单。若余额达不到要求，保持未发布状态，不对玩家承诺未来补发工资。
2. 按真实需求补缺：仅在玩家发起已有配送且位置/actor/库存等检查成立时，最多补到90；单次最多30。补贴只进入该world的公共基金，不能发给玩家、商家或用于恢复资源节点。发行、订单publish及其预留放在一个外层事务，任一失败全部回滚。没有需求、缺货或NPC不可用时不发行。
3. 硬限额：滚动24小时最多30、滚动7天最多210、world生命周期累计毛发行最多600、流通货币总量最多4000（当前初始3400）。每次发行间隔至少24小时；多个请求/进程串行检查持久记录，不能刷新或换epoch重置。回收不返还累计毛发行额度。重复请求使用相同凭证返回收据，不占第二份额度。
4. 明确来源：未来新增受信命令只接受政策凭证ID，内部核对world基金账户、策略版本、真实请求与既有额度；账本reason为公共配送流动性补助，source固定为world+policyVersion+request身份。分录为issuance负数、fund正数；消费者不能由event prose触发二次发行。
5. 回收仅来自明确可用盈余：若后续业务真实形成基金收入，可另设默认关闭的盈余回收策略，保持基金可用额至少180、单次/滚动24小时最多10，凭已结算收入来源去重，分录fund负数/issuance正数。先校验对既有预留无影响；不自动扣玩家离线钱包。当前基金净流为负，合理结果是回收0，不能为了数学平衡硬扣其他账户。
6. 时间异常：政策保存lastObservedAt；回拨时暂停新发行/回收，继续允许取消与退款。明显前跳也暂停待确认，不累计离线“每日额度”；单次恢复不会补发错过的天数。普通已承诺订单仍按原生命周期恢复，不靠发行复活过期订单。

推荐未来新增独立policy receipt/state表和受限经济命令，不让业务直接访问内部moneyChange，也不放开普通transfer对issuance的限制。新命令应校验同DB政策凭证、硬cap与目标账户，而不信任客户端传amount。schema、业务接入及具体策略启用均待main决定，本轮未实现。

### 决策与后续验收

该方案只是最多600的有界缓冲。按当前净支出10/轮，不能消除结构性流出，也不改变节点200的硬边界；若资源先耗尽，补贴必须停。长期修复需要已存在角色的真实消费/采购需求与资源政策，不能宣称增加货币就实现循环。

若main授权后续实现，最小验收应增加同SQLite文件并发争最后额度、同请求冲突、world重置不恢复总cap、回拨/前跳不刷额度、发行后publish失败整体回滚、库存不足零发行、账户余额含托管正确计算、取消只退款不再次发行、回收不侵占预留。所有政策参数在版本化配置中保留可审计值，先保持功能关闭。
