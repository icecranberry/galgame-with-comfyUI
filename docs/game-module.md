# 游戏模块接入

从主导航「游戏」或手机侧栏「更多 → 游戏中心」进入。官方跑团模拟器支持玩家 KP 与角色 KP 两种模式，内置《没有终点的末班车》《雾夜民宿的第四位房客》《苍白频道 404》。大厅根据所选模组的 HO 张数限制调查员人数，一次生成全员调查员卡。「随机选人」按模组推荐的调查员总数或范围抽取阵容，同时受 HO 容量和候选人数限制。模组未标注推荐人数时，在可用容量内抽取。玩家担任调查员时占一个调查员名额，并另选一位角色 KP。模型需支持原生工具调用才能使用角色 KP 模式。新牌局默认开启画面生成。

## 包与运行时

- 官方包：`games/official/<id>/`，随仓库发布；无需额外安装依赖或构建游戏前端。
- 社区包：`agent-core/data/games_community/<id>/`。工坊和仓库链接通过 Git 拉取默认分支，本地 ZIP 可单独导入。工坊结果缓存 20 分钟，失败可回用旧缓存。
- 存档：`installed_games`、`game_sessions`，与游戏包分离。社区游戏在 ID 和来源均匹配时可以恢复保留的数据，见[开发指南](linshe_community_game_guide.md#保留数据更新)。
- 图片：`agent-core/data/game/<id>/<sessionId>/`。只在游戏中展示，手动收藏后复制到主相册。删档与选择清数据的卸载会清理对应目录。
- HTTP 代理、GitHub Token 和 Raw 镜像前缀可在游戏中心「连接设置」保存。Git 拉取使用工坊代理，Token 只发送到 GitHub API。

清单与示例见 [开发规格](linshe_game_module_dev_spec.md) 和 [社区开发指南](linshe_community_game_guide.md)。`serverEntry` 为单文件 ESM，可以引用 Node 内置模块，第三方依赖须提前打包；安装时不执行 npm。后端插件是用户信任的本机代码，异步错误兜底和受控 `ctx` 不构成 Node 安全沙箱。

## 前端 SDK

游戏中心与宿主的 UI 独立于主站 Linshe 组件，沿用本地 `game-test`（`92af58cf`）的游戏馆风格。共用控件与弹窗位于 `web-ui/src/games/components/`，主题位于 `web-ui/src/games/styles/game-ui.css`；游戏包内部继续自行维护 UI。

宿主在 HTML 的游戏脚本之前自动注入 `/game-sdk.js`。使用 `await window.LinSheGameSDK.ready` 等待握手。前端资源使用相对路径，保留包内 `web/` 目录。iframe 不授予同源能力，禁止直接联网；通过 SDK 请求宿主，主站样式和浏览器存储不进入游戏。

```js
const sdk = window.LinSheGameSDK;
await sdk.ready;
const people = await sdk.bridge.call('get_characters');
await sdk.save.write('my-save', '第一幕', { chapter: 1 });
const save = await sdk.save.load('my-save');
await sdk.save.write('my-save', '第二幕', { chapter: 2 }, save.revision);
const stop = sdk.on('media', event => console.log(event.sessionId, event.url));
stop();
```

支持 `bridge.call`、`llm.chat`、`image.generate`、`image.promote`、`save.list/load/write/delete`、`ext.request`、`ui.exit`。桥接工具接受固定白名单：角色列表、完整资料、关系、立绘、记忆目录/搜索、相册、情绪和小镇状态，不提供设置、密钥、向量库管理或任意 HTTP 请求。

扩展路由注册在 `ctx.router` 下，由 SDK `ext.request('/path', { method, body })` 调用。`ctx.db` 是当前游戏的存档仓库，提供 `list/load/write`，没有全库 SQL 接口；权限仍由清单控制。`ctx.events.emit(type, data)` 通过 SSE 和 SDK 推送给当前游戏。插件默认导出注册函数，可返回 `onUnload()`，或导出同名清理钩子。停用、更新和卸载会清理插件，并取消其未完成的 LLM 请求。

## 跑团状态边界

规则引擎保存在官方包 `server/index.mjs`。前端通过扩展接口推进和读取卷宗，通用存档接口只提供跑团目录和删除。每个存档串行处理规则操作。`POST /advance` 只写播放位置，可以与回合演算并行。

`POST /turn` 接受客户端生成的 `turnId`。启动回合时，玩家发言和回合编号一起入档。角色 KP 的完整工具请求先入档，每个工具结果与对应状态变更在同一次 SQLite 写入中提交。HTTP 断开会取消当前模型请求。重新载入后用 `GET /state` 返回的 `pendingTurn.id` 作为 `turnId` 重发，可附带 `resume: true`，已记录的工具结果继续用于原模型会话。回合已完成时，同一编号返回当前状态。每轮模型最多为玩家掷一次骰，每名调查员的普通 HP/SAN 调整合并为一次。手动 `/roll` 和 `/control` 使用各自的 `operationId` 去重，重发返回原操作结果；`checkId` 可绑定具体的待掷骰检定。

服务端先保存演算结果，前端按顺序自动播放本轮首句回应及其前面的道具、线索等记录。点击舞台逐帧阅读后续普通叙事。播放位置随存档保存，读档后可从原位置继续。场景跟随已播放的画面。新领道具在领取记录出现时显示在背包，本轮播完后可使用。线索、道具消耗和角色状态在本轮播完后同步。角色 KP 模式中的玩家检定和 AI 队友检定在后台完成。播放到检定请求或骰值时自动进入掷骰，动画结束后接到 KP 裁定首句。

玩家担任 KP 时，AI 调查员在第一项具体行动意图处停下。该条发言提供「直接描述结果」与「要求检定」。后者在 `/roll` 中传入 `actionLogId`，由服务端绑定发言者并保存一次骰值。「描述检定结果」位于对应的明骰或暗骰结果卡中。两条路径都通过 `/describe-action` 发布 KP 写下的结果。完成检定裁定时同时保存待回应的回合，只有执行检定的 AI 调查员回应，首句紧接 KP 裁定自动播放。角色 KP 为 AI 队友裁定检定时也遵循同样的发言顺序。存档保留未完成的裁定、骰值和回应。技能、难度、骰型与暗骰在打开检定时选择，控制台的「临时检定」可独立处理突发事件。

常规回合由同一次请求扮演全体在场 AI 调查员，角色 KP 独立调用。方括号表情前缀决定调查员发言时的立绘，KP 的发言以字幕呈现。玩家担任调查员时，`[玩家:表情名]` 可在同一画面切换玩家立绘，包括对 KP 叙事的反应。当前回合播放完毕且等待玩家行动时，操作栏显示可填入草稿的行动方向，由已有的回合请求一并生成。

回合提示词沿用神说的消息追加方式。KP 和调查员组各自冻结已注入常驻世界书的固定前缀。阵容沿用群聊的 `<group_info>` 成员卡结构，按姓名列出每人的 `short_prompt`、本局公开身份与擅长项。调查员组在同一请求中逐人输出发言，`speaker` 填姓名。KP 的目标工具与状态差量也使用姓名，服务端按阵容映射到内部角色记录，同名角色使用席位区分。跨轮按公开卷宗的顺序还原消息，已确认的 AI 发言和叙事作为 assistant，玩家发言和引擎记录作为 user。技能和底卡属性由引擎读卡裁定，HP、SAN 等当前状态按角色及字段增量发送。状态差量、本轮触发的世界书和当前任务随末条 user 快照保存。原始 KP 工具配对及推理字段只用于本轮的工具续调用和断点恢复。

输入预算为 `min(500000, 模型窗口 − 输出预留, 模型单独声明的输入上限)`。模型窗口和输出上限读取当前渠道的模型元数据，输出预留以实际发送的生成上限为准。渠道未声明窗口时，可用 `TRPG_MODEL_CONTEXT_WINDOWS` 按模型名提供 JSON 映射。两者都缺失时，以 32,768 的保守窗口和至多 8,192 的输出上限运行。服务端按 token 估算整个请求，计入固定前缀、世界书、工具定义和续轮。估算达到预算约 90% 时，先合并状态快照，保留公开对话原文。合并后仍超过归档线时，优先按完整回合将更早公开记录归档至约 75%。整局公开卷宗仍可查看，官方跑团存档上限为 32 MiB。服务商实际输入和缓存命中读取 LLM 客户端 `[cache]` 用量。

有风险且结果不确定时才检定。默认 D20，技能修正为 `floor((技能值 - 50) / 10)`，普通、困难、极难的目标值分别是 10、14、18。自然 20 大成功，自然 1 大失败。优势或劣势各掷两颗 D20，分别取高值或低值。D20 结果卡左侧显示骰面和技能修正，右侧标注结算值。滚动时先显示栏位和已知修正，停骰后揭晓骰面与结算值。D100 在需要百分骰时使用，1 大成功，96–100 大失败，普通、困难、极难按技能全值、二分之一、五分之一确定阈值。理智检定默认以当前 SAN 掷 D100。玩家检定回执和队友待裁定数据向 KP 提供引擎结论 `outcome`、调查员、技能名和行动理由。KP 根据结论叙述后果。随机表和伤害等可调用 `roll_dice`，支持 1–6 颗 D3、D4、D6、D8、D10、D12、D20 或 D100，返回每颗骰值和合计。

HP 或 SAN 为零自动退场，允许引入新角色替补或结团。结团记忆默认不写入；用户勾选后以明确的“虚构桌游／剧本杀经历”保存，并按存档去重。

模组可用 `scenario.rules` 声明队伍道具、关键动作及结局。公开发放关联线索会登记道具，关键动作可要求场景、已得线索、持有道具、前置动作或场内成功检定。引擎负责消耗道具、发放新道具、扣减状态和锁定达成结局。有结构化规则时，`/finish` 需要已达成结局，或显式传 `abandon: true` 提前收团。旧存档沿用自己的剧本快照，当前三份官方模组按原文进行自由裁决。

## 行囊背包

「线索卷宗」保留线索与密信，「随身道具」显示调查员持有和全队共享的实物。个人道具存在调查员 `inventory`，新增共享道具存在存档 `partyInventory`。旧的字符串道具读档后视为不限次的剧情物品。模组原有的队伍关键道具以同一结构显示，继续沿用 `progress.held` 和 `progress.spent` 处理解锁与消耗。

玩家 KP 用扩展接口 `POST /give-item` 发放道具。`targetChar` 填调查员 ID 或 `party`，手填时提供 `name`、`type`、`desc`、`effect`、`uses`，随机发放时传 `random: true`。随机道具按当前公开场景和目标最近的大成功或大失败生成。角色 KP 使用同一套发放逻辑，工具 `give_item` 的 `targetChar` 接受成员卡姓名或 `party`。

`POST /use-item` 接受 `itemId` 和使用者 `targetChar`。玩家 PL 使用自己的道具或共享道具，玩家 KP 可为在场调查员操作。发放与使用均支持 `operationId` 去重。消耗品结算 HP 和 SAN，有限次数用尽后留在背包标记为已耗尽。工具将加值挂到下一次对应技能检定，D100 使用调整后的技能值，D20 将调整后的技能值换算成骰面修正。幸运检定以 POW 为基础。同一技能同时只能备好一项加值。拿出关键物品或趣味杂物会写入叙事，由 KP 裁定。AI 调查员可以用 `useItemId` 使用持有或共享的道具，引擎先使用道具，再处理该次检定。

## 秘密 HO

剧本可声明 `handouts`，每项包含 `id`、`title`、`publicSummary`、`secretContent`、`recommendedTrait`。大厅目录用 `handoutCount` 提供阵容容量。开局时，服务端从整副牌随机抽取，每位调查员领取一张且互不重复。玩家担任 PL 时和 AI 调查员一起抽取。HO 随存档保存，读档沿用原分配。未发放的牌留在牌堆里，有替补入场时从中随机抽取。

大厅以草稿编号保存导入剧本，玩家 KP 可以查看和编辑全文。玩家 PL 开局后在「秘密 HO」查看自己的卡。玩家 KP 在同一页查看全员卡并选中调查员，进入既有检定及密信控件。角色 KP 在主持上下文获得全员秘密。调查员组的人设卡在角色 `short_prompt` 上叠加 HO 标题及公开身份。剧本可额外用 `investigatorRoles` 按调查员席位提供 `{ title, publicSummary }`，无需指定身份的席位可用 `null`。HO 密文和私信由 KP 按剧情推进及揭露。

开场、切场和极端骰值继续自动生成舞台背景。牌局启用生图时，玩家 KP 可在发言区打开「配图」。发送发言时以该段发言为素材。输入为空并点「自由行动」时，以本轮生成的调查员行动为素材，未产生新发言或行动时跳过。开关在当前牌局页面内持续生效，默认关闭。画面挂在对应叙事条目下并随该条目揭示。续跑使用已保存的配图选择。

角色 KP 可调用 `generate_image` 安排生图，环境空镜可用作场景背景，主动登记的情境在 `illustrations` 中按事件编号持续保留。两种主动拍摄都由图片实验室读取角色、润色提示词并传入奇遇生图参数。玩家 PL 只收到图片及显影状态。玩家 KP 可在印相中查看原始描述。

生图在后台运行，结果合并到最新存档。服务重启或生成失败后可重试同一张，发起时登记的事件只入档一次。失效存档拒绝图片落盘。

## 验证范围

开发验证使用隔离 SQLite、临时安装目录和确定性 LLM/生图桩，覆盖导入、权限、存档、插件异常、两种模式、发言断点、私密上下文、退场、幕间摘要及浏览器 SDK 流程。HO 集成验证检查目录、导入草稿、双模式分配、读档以及实际交给 KP 和各 AI 调查员的提示词内容。此前使用真实模型走完旧版古宅和列车模组，验证了断线续跑时骰值及扣减只结算一次。ComfyUI/NovelAI 连通和写入长期记忆仍待专门联调。
