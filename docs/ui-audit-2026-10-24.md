# 项目 UI 巡查报告

- 巡查日期：2026-10-24
- 巡查范围：16 个 Web 页面、共用控件、主要业务弹窗，以及原生启动器各页面。
- 设计依据：[设计系统](design-system.md)、[项目 AGENTS.md](../AGENTS.md) 及本次会话提供的项目约定。
- 工作性质：只读巡查与优化建议，未修改业务代码；本文件为巡查结果归档。
- 证据边界：代码检查覆盖各模块；真实截图仅抽查部分页面，不能视为全部页面、主题及交互状态均已通过验证。

## 1. 结论与优先级

现有 Cel Glow / Linshe 体系可以继续保留。优先解决输入保护、失败反馈、筛选恢复与操作可达性，再收敛内容层级、排版和动效，不需要整体更换视觉体系。

| 优先级 | 含义 | 建议处理范围 |
| --- | --- | --- |
| P1 | 可能误触发送、覆盖配置，或使关键操作无法恢复 | 私聊输入法保护、奇遇筛选恢复、记忆设置读取失败保护 |
| P2 | 影响操作反馈、键盘使用、内容可达性或规范一致性 | 加载与失败状态、保存与草稿保护、弹窗与下拉框、小镇服务链路、手机标题遮挡 |
| P3 | 不阻断使用，但能提升浏览效率与阅读舒适度 | 酒馆入口占位、更新说明布局、说明文字、日志检索 |

下文“代码确认”指实现中存在相应结构或缺失；描述的运行影响仍需按验收条件实测。“截图确认”仅证明截图中的可见现象，不代表对应交互流程已经验证。

## 2. 各模块巡查清单

### 2.1 私聊：输入法回车可能提前发送（P1）

- **证据类型**：代码确认，未发送消息实测。
- **现状**：输入框直接使用 `@keydown.enter.exact.prevent="send"`，发送入口没有输入法合成判断。中文输入法选词时按回车，可能发送尚未编辑完成的草稿。
- **建议**：复用群聊已有的 `onSendKey` 模式，先判断 `event.isComposing`，确认不是输入法选词后再阻止默认行为并发送。
- **位置**：[ChatView.vue](../web-ui/src/views/ChatView.vue)，巡查时第 194、1782 行；参考 [GroupChatView.vue](../web-ui/src/views/GroupChatView.vue) 第 944 行。
- **验收**：中文选词回车只完成选词；普通回车发送；Shift+Enter 换行；鼠标发送行为保持一致。

### 2.2 奇遇：空筛选结果隐藏恢复入口（P1）

- **证据类型**：代码确认。
- **现状**：往期区域由 `filteredHistory.length > 0` 控制，筛选工具栏也在这个区域内部。选择没有匹配历史的角色或“只看参与过的”后，往期区域和“全部”按钮一起消失；筛选还会影响活跃列表。
- **建议**：按原始数据或当前筛选状态保留工具栏；空结果展示“没有匹配的奇遇”及“清除筛选”，不要把过滤结果为空解释成没有任何奇遇。
- **位置**：[EventsView.vue](../web-ui/src/views/EventsView.vue)，巡查时第 85、98 行；[events.js](../web-ui/src/stores/events.js) 第 39、46 行。
- **验收**：筛选到零结果后，仍能直接恢复全部内容，无需刷新或重新进入页面。
- **补充优化（P2）**：初次读取及生成失败不能只写控制台；应显示失败说明、提供重试并保留生成方向草稿。
- **补充优化（P3，截图确认）**：手机截图显示当前没有活跃奇遇，但存在大量往期记录。空状态宜明确“当前没有进行中的奇遇”，并引导使用已有的往期内容或“扰动世界线”操作。

### 2.3 记忆设置：读取失败后仍可保存默认配置（P1）

- **证据类型**：代码确认。
- **现状**：初次加载失败仅显示 Toast，随后结束 loading 并进入完整表单；保存按钮没有以成功读取为前提。用户可能将初始化默认值当作现有配置保存。
- **建议**：增加 `loaded / loadError` 状态，读取成功前禁止保存；读取失败时显示就地重试。
- **位置**：[MemorySettingsView.vue](../web-ui/src/views/MemorySettingsView.vue)，巡查时第 20、175、715、727 行。
- **验收**：首次读取失败时不能提交配置；重试成功后才开放编辑和保存。
- **补充优化（P2）**：高级设置仅通过高度和溢出裁切收起，隐藏控件仍可能被 Tab 聚焦。收起期间应设置 `inert`，过渡完成后再隐藏或卸载，展开时恢复。

### 2.4 系统设置：手机标题遮挡及保存反馈（P2）

- **证据类型**：标题混叠为截图确认；保存反馈为代码确认。
- **现状**：手机滚动状态下，“最大输出 tokens”等表单文字从固定标题上方露出，表单延伸到“系统参数”标题背后。部分说明采用 12px 字号，部分多行说明行高仅约 1.2。画风尺寸及 LLM 保存操作缺少完整的保存中互斥；保存期间继续编辑还可能被旧响应覆盖或错误清除未保存标记。
- **建议**：为固定标题提供完整的覆盖区域，避免顶部缝隙透出表单；区分必需说明与参考信息，调整字号、行高与间距。每组配置使用独立 saving 状态和 Linshe loading，按提交快照判断是否仍有后续草稿。
- **位置**：[SettingsView.vue](../web-ui/src/views/SettingsView.vue)，巡查时 `onSettingsScroll`、`saveComfy`、`saveLlmConfig`、`.page-header` 移动端样式及 `.fd` 样式；归档前对应约第 1296、2424、2641、3249、3834 行。
- **验收**：390×844 下暖色和暗夜滚动均无标题与表单混叠；慢网保存有明确反馈；保存失败或保存期间继续编辑时，不丢失草稿。

### 2.5 小镇：统一服务链路及游戏界面（P2）

- **证据类型**：代码与本次项目约定对照；未验证完整小镇运行画面。
- **现状**：`TownView` 挂载独立 `TownShopStage`，组件仍走不跳奇遇页的 quote/execute 流程；NPC 服务也存在直接打开服务舞台的路径。店铺使用独立深木像素皮肤、普通裸按钮，与本次规定的“奇遇唯一链路”、暖纸对话舞台和 Linshe 控件口径存在差异。
- **建议**：先统一产品入口与服务推进方式，再收敛视觉；建筑和 NPC 服务按约定进入奇遇叙事，保留钱包及赠礼/交易轻结算。不要只换皮肤而继续维持两套服务流程。
- **位置**：[TownView.vue](../web-ui/src/views/TownView.vue) 第 251 行；[TownResidentActions.vue](../web-ui/src/components/town/TownResidentActions.vue) 第 84、142 行；[TownShopStage.vue](../web-ui/src/components/town/shop/TownShopStage.vue) 第 67、245 行。
- **验收**：NPC 邀请、建筑服务和特殊奇遇入口符合统一链路；桌面、手机、暖色及暗夜均与 `TownDialogueStage` 保持一致。
- **补充问题（P2）**：货摊商品卡的详情点击与内部“买下”按钮事件会冒泡叠加，点击购买可能同时打开详情。应阻止内层购买事件冒泡，或缩小详情热区。[TownNpcTradePanel.vue](../web-ui/src/components/town/TownNpcTradePanel.vue)，第 22、39 行。

### 2.6 朋友圈：筛选后的较早内容可能不可达（P2）

- **证据类型**：代码确认。
- **现状**：初次只加载最新一批内容，角色、点赞及本人筛选在本地执行。后续加载依赖滚动事件；筛选结果不足一屏或完全为空时，用户无法滚动触发续页，而更早批次可能仍有匹配内容。
- **建议**：优先使用按筛选条件分页；或通过可见页尾自动继续查找，同时提供“加载更早动态”。确认没有更多匹配内容后才展示最终空态。
- **位置**：[moments.js](../web-ui/src/stores/moments.js)，第 9、38、100 行；[MomentsView.vue](../web-ui/src/views/MomentsView.vue)，第 99、102、307 行。
- **验收**：首批零匹配而较早批次有匹配时，用户仍能找到内容；首屏失败与真正空数据明确区分。

### 2.7 信箱：寄送失败与草稿保护（P2）

- **证据类型**：代码确认；列表布局已做手机截图复核。
- **现状**：寄送失败只写控制台，按钮恢复后没有明确结果提示；顶部返回和底部取消会立即清空收信人与正文。
- **建议**：寄送失败就地说明并允许重试，保留正文和收信人；按收信人暂存草稿，成功寄送后再清除，显式放弃时确认。
- **位置**：[MailboxView.vue](../web-ui/src/views/MailboxView.vue)，第 158、184、329、336 行。
- **验收**：断网寄送不丢正文；误触返回可恢复长信；重试前能明确知道上次是否成功。
- **保留**：手机列表的暖纸底、深棕文字、信封图形和紧凑状态行，本轮未见需要重做的布局问题。

### 2.8 群聊：设置提交状态不完整（P2）

- **证据类型**：代码确认。
- **现状**：保存按钮仅按成员数禁用，没有完整 loading、重复提交守卫和就地失败反馈。
- **建议**：保存期间锁定相关操作，区分保存失败与保存成功后刷新失败；失败保留编辑草稿。
- **位置**：[GroupChatView.vue](../web-ui/src/views/GroupChatView.vue)，第 360、1035 行。
- **验收**：慢网下只能提交一次；失败原因可见；重试不需要重新填写。

### 2.9 相册：空态与失败状态混淆（P2）

- **证据类型**：代码确认。
- **现状**：首次请求失败可能表现为“空相册”，加载反馈不足；部分头像筛选和图片卡片仅支持鼠标点击。
- **建议**：明确初载、成功为空、加载失败和续页失败；提供就地重试。图卡按整卡热区规范补齐焦点、Enter/Space 和名称。
- **位置**：[Gallery.vue](../web-ui/src/components/Gallery.vue)，第 55、82、396 行。
- **验收**：接口失败不提示“没有图片”；键盘可筛选并打开图片，关闭预览后焦点返回原图卡。

### 2.10 日程：缺少清晰的初载与失败反馈（P2）

- **证据类型**：代码确认。
- **现状**：请求失败主要写控制台，页面容易显示为“没有日程”，可能误导用户重新生成。
- **建议**：补充初载骨架及错误状态，保留已加载内容；刷新失败时提供重试，而不是切换到空态。
- **位置**：[ScheduleView.vue](../web-ui/src/views/ScheduleView.vue)，第 7、63 行；[schedule.js](../web-ui/src/stores/schedule.js)，第 107 行。
- **验收**：网络失败与未生成日程可区分；失败后存在明确恢复路径。

### 2.11 背包：详情关闭与键盘链路不完整（P2）

- **证据类型**：代码确认。
- **现状**：道具详情缺少明显关闭按钮、Esc、dialog 语义和焦点管理；选择角色的卡片仅支持点击。
- **建议**：复用统一弹窗行为，保留业务内容布局；补齐整卡的键盘激活与状态表达。
- **位置**：[BackpackView.vue](../web-ui/src/views/BackpackView.vue)，第 168、192、200 行。
- **验收**：键盘能完成打开道具、选择角色、取消及退出；关闭后恢复原焦点。

### 2.12 独立立绘：未生成与加载失败混淆（P2）

- **证据类型**：代码确认。
- **现状**：首次同步失败可能留下空白；图片预加载失败可能转成“未生成立绘”；断连时保留旧画面但没有同步提示。
- **建议**：分别表达连接中、尚未选择角色、未生成、图片失败和断连；失败可重试，断连保留旧画面并给轻量状态提示。
- **位置**：[StandingDisplayView.vue](../web-ui/src/views/StandingDisplayView.vue)，第 4、132、142 行。
- **验收**：图片暂时不可达时不会引导用户重复生成；恢复连接后状态自动更新。

### 2.13 MaiBot：自动保存失败后状态不明确（P2）

- **证据类型**：代码确认。
- **现状**：配置改变后自动保存，失败只有短 Toast，控件仍呈现新值；保存状态没有完整接入实时 UI。
- **建议**：使用响应式保存状态及最后成功快照，显示“保存中／未保存／重试”，失败保留草稿。
- **位置**：[MaibotBridgeView.vue](../web-ui/src/views/MaibotBridgeView.vue)，第 81、92、333、353 行。
- **验收**：自动保存失败后，用户能辨认当前值尚未生效，并能直接重试。

### 2.14 酒馆：角色区管理入口占位偏大（P3）

- **证据类型**：截图确认；键盘问题为代码确认。
- **现状**：桌面角色区首排六格中，表情包、立绘、音色管理和招募占四格，真实角色仅占两格，工具操作与人物同尺度竞争注意力。
- **建议**：压缩现有管理入口的占位和视觉权重，让人物浏览成为角色区主体；不改变关系图整行、世界观与预设并排的既有结构。
- **位置**：[TavernView.vue](../web-ui/src/views/TavernView.vue)，第 245、275、281 行。
- **验收**：同一视口能更直接看到角色，管理动作仍容易找到；信箱、背包、表情管理、招募等整卡入口补齐键盘操作。

### 2.15 媒体：保留为状态处理参考

- **证据类型**：代码检查。
- **现状**：已有加载骨架、失败重试、分页页尾自动补足、灯箱 Teleport 层级及漫画风 token。
- **建议**：本轮不建议重做，可将加载与分页处理作为相册、朋友圈等模块的参考。
- **参考位置**：[MediaView.vue](../web-ui/src/views/MediaView.vue)，第 548、1266、1291 行。

### 2.16 AstrBot：进行中代码的合入前检查

- **证据类型**：巡查期间新增代码的只读补查，不列为稳定版本正式缺陷。
- **现状**：Web 页面已有 Linshe 组件、初载失败重试、未保存状态、操作 loading、0.3 秒过渡和窄屏布局；启动器页面复用现有按钮、开关和日志，并按安装与运行状态控制操作。
- **检查建议**：保存期间继续编辑时，旧请求返回值可能覆盖当前草稿。按提交版本保留后续修改，或保存期间禁用相关表单。
- **位置**：[AstrbotBridgeView.vue](../web-ui/src/views/AstrbotBridgeView.vue)，巡查时第 109 行；[astrbot_page.py](../launcher/launcher/astrbot_page.py)。

统一状态建议：初次加载、成功为空、初次失败、有旧内容的刷新、续页失败、提交中、提交失败，应分别表达。不要以统一的“暂无内容”替代所有状态。

弹窗补查还发现：事件/话题库设置了 loading，但主列表未消费，慢网时会提前出现空态，读取失败缺少列表内重试；音色库部分加载及错误段落缺少明确内容样式。世界书、预设、服装管理现有的响应式、草稿及预览组织较完整，本轮没有提出整体重做建议。

未将以下情况误判为统一组件违规：隐藏文件上传 input、range 控件、聊天主输入框、信纸 textarea、已有独立设计的特殊控件，以及信箱／Toast／世界观的暖纸主题例外。自动检查中的隐藏侧栏、不可见内容和必要白色内衬嵌套，也未直接计入视觉缺陷数量。

## 4. 原生启动器
